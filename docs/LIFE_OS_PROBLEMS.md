# 人生运行系统第3步交付（2026-11-26）

## 已实现与使用

登录后访问 http://127.0.0.1:8000/life-os 。顶部自然对话完成后，核心分析同一次调用提取事件和问题，不额外逐模块调用模型。第二块“我的人生问题说明书”按确认的独立事件次数降序、最近事件日期降序展示四列：次数、问题、默认处理机制、备注。

1. 描述真实发生的一件事，保存并分析。
2. 继续描述同一次事件或报告已做的行动，不应增加该问题次数。
3. 不确定是否同一事件时生成待确认记录，不计数；从“事件管理”确认或修改问题归属。
4. 点击问题可看事件、完整原文、该轮状态/建议、AI观察、用户报告的实际行动和效果。无反馈显示“效果待验证”。当前实际模式尚属第5步；这里只能读取已有AI建议模式，明确区分。
5. “管理问题”可改名称、默认机制与备注，查看历史、合并误分类问题或软删除。手动保存的字段不被AI覆盖；合并保留目标手动内容，旧问题当前内容和历史仍保存。
6. 每条原文可修正到其他已有事件，或拆成新的独立事件；也可修改事件与问题的关联。计数实时重新查询。
7. 可直接在事件下填写实际方法、结果和效果判断，重复提交同一操作编号不重复记录。反馈历史追加保存。

## 杂念只读授权

默认不读取杂念。顶部展开查询本人的有效杂念，最多选择3条、每条不超过1500字作为本轮背景；查询不调用AI，不修改杂念原文、版本、分类、次数。原文过长明确拒绝，不静默截断。

杂念背景不会自动形成计数。若要登记历史事件，在问题区明确选择杂念来源、新事件或已有事件、问题归属并确认。一个杂念来源只能有一个事件归属；重复登记会被拒绝或按原操作编号返回原结果。同一事件关联主对话与历史杂念也只算一次。杂念日期默认取记录日期，实际发生日期可在事件管理校准。

读取与发布前均校验归属、有效状态与版本。删除杂念后，不再展示该原文；只剩删除杂念来源的事件不再计数。记录AI分析的note_scope，取消选择、删除或来源版本变化后，不将依赖该来源的旧回复/状态直接续发。问题经验是已保存的派生记录，仍须区别于杂念原文与用户实际反馈。

## 数据与一致性

0029_life_os_problems：增量新增6张表 life_os_problems、life_os_events、life_os_event_sources、life_os_event_problems、life_os_experiences、life_os_problem_history；分析表新增note_scope、experience_status、experience_error三个可空字段。

- 问题类型、具体事件、原始消息分离。
- event_sources对每个owner/message、owner/note设唯一约束；每事件/问题关联主键唯一。
- 次数由SQL查询已确认、有效来源的事件得到，模型没有次数输入字段。
- 已关联原文重新分析不会新建事件，也不撤销人工修正；必要时通过人工管理修改。
- 同源校验、用户锁、owner复合FK、乐观版本与操作回执防止越权、并发覆盖和重复写入。
- 原文不可变，AI建议、观察、用户报告的行动、用户报告的反馈分开保存。自动提取的行动/反馈必须带当前消息中的逐字引用；语义判断仍可能有误，详情中展示依据并支持追加用户反馈。
- 核心成功结果先保存。可选事件字段不合法、无效引用、来源变化或附加写入失败，有独立状态/错误，不删除成功核心快照。完整JSON截断仍拒绝，不能从不完整JSON拼凑成功。
- 没有队列、后台模型轮询、自动付费重试；失败后用户可手动重分析。普通GET不调用模型。

## 有界AI上下文

沿用life_os_core，4096输出预算与90秒超时。最近消息仍最多6条，问题/事件/已选杂念上下文总JSON长度不超过7000字符；最多20个问题候选和10个近期事件，并优先保留近期对话已有关联事件。机制/备注使用短摘要，经验只取必要近期记录。没有发送全库历史、任务、他人记录或图片。

候选上下文有限，因此久远事件或同义问题可能未匹配。保守使用待确认和人工合并/归属修正；不宣称语义去重百分之百正确。历史第2步对话不会自动批量回填，重新分析或继续对话才逐步进入本库。
